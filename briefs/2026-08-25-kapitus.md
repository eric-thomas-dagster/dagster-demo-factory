# Kapitus — demo brief

## Demo thesis

Kapitus just brought on a new owner (InterVest Capital Partners, announced
Jul 27, 2026) and is mid-hire on a VP of Data Technology explicitly tasked
with building a data engineering org "from the ground up" and bringing
disparate, Airflow-orchestrated pipelines into one governed strategy. They
already ran a hands-on technical POC directly against Dagster+ (Jul 22–Aug

turns "we tested it and it worked" into "here is the governed, observable
lending data platform Kapitus is buying," reusing Kapitus's own asset names

# Build directives

## Asset graph

Model Kapitus's own lending data flow, using their real product-line
vocabulary, ~14–18 assets:

- **Ingestion** (`ingestion` group): `raw_loan_applications` (Fivetran, from
  the loan origination system), `raw_bank_statement_data` (S3 landing, fed by
  an OCR/analytics step — mirrors their real Ocrolus-style statement
  ingestion), `raw_credit_bureau_pulls` (S3 landing via Lambda). Partition on
  a daily key; add a second `product_line` partition dimension
  (`term_loan`, `revenue_based_financing`, `equipment_financing`, `sba_loan`,
  `line_of_credit`) via `MultiPartitionsDefinition` — this is a genuine
  domain axis for Kapitus (5 real product lines) and sets up a
  targeted-recovery story ("rerun just the SBA partition for 8/12").
- **Transformation** (`dbt` project, real dbt Core + DuckDB in demo mode):
  staging models per source, then marts — `funded_loans_daily`,
  `portfolio_performance_by_product`, `credit_risk_summary`. Real
  `schema.yml` tests, real lineage.
- **Reporting / decisioning** (`analytics` group): `daily_funding_summary`
  (feeds the exec view), `underwriting_decision_metrics`.

## Native integrations to use

- `dagster-dbt` for the transformation layer (mandatory — this is their
  stated stack).
- `dagster-fivetran` for the ingestion assets, badged `kinds={"fivetran"}`.
- `dagster-aws` (S3 sensor/resource) for the S3-landed sources; consider an
  EventBridge-triggered sensor pattern for `raw_credit_bureau_pulls` since
  AE notes call out "test invocation from eventbridge or surface state to
  Dagster" as an explicit POC criterion — search the registry for an
  eventbridge/SQS-triggered ingestion component before falling back to a
  custom sensor (see Component escalation ladder in CLAUDE.md; LEARNINGS.md
  already records that no registry component covers a partitioned,
  demo-mode-fakeable "poll an inbound file" source for ADLS — check whether
  the same gap exists for S3/EventBridge, and record what you find either
  way).
- `dagster-snowflake` kinds badges throughout (execution stays DuckDB in demo
  mode per `templates/demo_mode_pattern.py`).

## Asset checks

At least three, each mapped to a named pain:
1. **Blocking** — `raw_loan_applications` funded amount must be non-negative
   and within a sane bound; nothing downstream computes on a corrupted
   funding record. Answers "no unified data quality control" pain.
2. **Schema-change check** on the Fivetran-sourced loan application asset —
   directly the "Fivetran: test data quality happening upstream" POC
   criterion.
3. **Freshness** (as a check or via freshness policy — see below) on
   `funded_loans_daily` — answers "how would we know something broke,"
   which is the VP Data Technology req's core mandate.
